# رابط برنامه‌نویسی (API) — Car Control Pro

دو رابط مستقل وجود دارد:

1. **HTTP** روی Access Point داخلی (پنل وب و هر کلاینت دیگر)
2. **BLE** با پروتکل JSON خط‌به‌خط (برای اپ موبایل)

---

## ۱. HTTP

- پایه: `http://192.168.4.1` (AP) یا `http://pride.local` (با mDNS)
- احراز هویت اختیاری: اگر `API_PIN` تعریف شده باشد، هدر `X-Key` لازم است
  (روی `/cmd`، `/test` و `/set_config`).

### ۱.۱ endpointهای صفحه و وضعیت

| متد | مسیر | توضیح |
|------|------|--------|
| `GET` | `/` | پنل وب کامل (HTML فارسی RTL) |
| `GET` | `/get_sensors` | JSON وضعیت زنده: موقعیت، جهت، ولتاژ، جریان، توان، عدم‌قطعیت |
| `GET` | `/diag` | JSON دیاگنostics: ورودی‌های لمسی، صف، کیفیت کالیبراسیون، سلامت |
| `GET` | `/logs` | JSON آخرین رویدادهای لاگ |
| `GET` | `/log.csv` | خروجی CSV لاگ (قابل دانلود) |
| `GET` | `/logclr` | پاک‌کردن لاگ |
| `GET` | `/get_config` | JSON تنظیمات ظاهری پنل |
| `POST` | `/set_config` | ذخیرهٔ تنظیمات ظاهری (JSON، حداکثر ۵۱۲ بایت) |
| `GET` | `/update` | صفحهٔ OTA (ElegantOTA) |

### ۱.۲ endpointهای کنترلی کوتاه

| مسیر | معادل فرمان |
|------|--------------|
| `GET /d_up` | بالا بردن شیشهٔ راننده (تا انتها) |
| `GET /d_down` | پایین آوردن شیشهٔ راننده |
| `GET /d_stop` | توقف شیشهٔ راننده و خالی‌کردن صف |
| `GET /p_up` | بالا بردن شیشهٔ شاگرد |
| `GET /p_down` | پایین آوردن شیشهٔ شاگرد |
| `GET /p_stop` | توقف شیشهٔ شاگرد |
| `GET /vent` | اجرای صحنهٔ تهویه (هر دو شیشه تا ۱۵٪) |
| `GET /lock` | پالس رلهٔ قفل مرکزی |
| `GET /unlock` | پالس رلهٔ بازکردن قفل |
| `GET /set_time` | هم‌زمان‌سازی ساعت دستگاه |

### ۱.۳ `GET /cmd` — پارامترها

پارامترهای `w` (شیشه: `0` = راننده، `1` = شاگرد) و سایر پارامترها ترکیب می‌شوند.

| پارامتر | مقدار | اثر |
|----------|-------|-----|
| `w` | `0` \| `1` | انتخاب شیشه |
| `d` | `1` \| `-1` \| `0` | جهت حرکت؛ `0` یعنی توقف |
| `b` | `0` \| `1` | حالت دستی/اتوماتیک |
| `auto` | — | اجرای حرکت اتوماتیک (تا انتها) |
| `goto` | `0..100` | رفتن به درصد مشخص |
| `cal` | `arm` \| `cancel` \| `close` \| `open` \| `done` | مدیریت کالیبراسیون |
| `calreset` | — | بازنشانی کالیبراسیون شیشهٔ انتخاب‌شده به مقادیر پیش‌فرض |
| `scene` | `close` \| `open` \| `vent` \| `park` \| `safety` | اجرای صحنه |
| `lock` | `0` \| `1` | وضعیت قفل مرکزی |
| `child` | `0` \| `1` | قفل کودک |
| `autoLock` | `0` \| `1` | قفل خودکار |
| `autoRain` | `0` \| `1` | بالا بردن خودکار در باران |
| `tap` | `60..800` | آستانهٔ لمس (میلی‌ثانیه) |
| `mx` | `3..30` | حداکثر زمان رله (ثانیه) |
| `sag` | `0` \| `1` | فعال‌سازی تشخیص افت ولتاژ |
| `sagv` | `0.05..2.0` | آستانهٔ افت ولتاژ (ولت) |
| `gest` | `0` \| `1` | فعال/غیرفعال ژست‌ها |
| `gup` / `gdn` | `0..2` | صحنهٔ دابل‌تپ به بالا / پایین |
| `gtu` / `gtd` | `0..5` | صحنهٔ تریپل‌تپ به بالا / پایین |
| `time` | unix | هم‌زمان‌سازی ساعت |

**نمونه‌ها:**

```bash
# بستن شیشهٔ راننده
curl "http://192.168.4.1/cmd?w=0&d=1"

# رفتن شیشهٔ شاگرد به ۴۰٪
curl "http://192.168.4.1/cmd?w=1&goto=40"

# اجرای صحنهٔ پارک
curl "http://192.168.4.1/cmd?scene=park"

# شروع کالیبراسیون شیشهٔ راننده
curl "http://192.168.4.1/cmd?w=0&cal=arm"

# تغییر حداکثر زمان رله به ۱۰ ثانیه
curl "http://192.168.4.1/cmd?mx=10"
```

### ۱.۴ `GET /test` — تست رله‌ها

پارامترها: `pin` (شمارهٔ GPIO) و `ms` (مدت پالس).

```bash
curl "http://192.168.4.1/test?pin=15&ms=500"
```

ریلی‌های تست در حین تست، موتورهای واقعی را قفل می‌کنند و بعد از پایان تست، وضعیت قبلی
بازیابی می‌شود.

### ۱.۵ `GET /led` — کنال‌های روشنایی

کانال‌ها: `int` (چراغ داخل کابین)، `sq` (چراغ مربعی سقف)، `rear` (آنتی‌هدلایت عقب)،
`foot` (چراغ زیرپایی).

| پارامتر | مقدار |
|----------|-------|
| `k` | کانال: `int` \| `sq` \| `rear` \| `foot` |
| `mode` | `steady` \| `flash` \| `dance` \| `police` \| `plane` |
| `pat` | `wave` \| `chase` \| `rand` |
| `br` | روشنایی (۰ تا ۱۰۰) |
| `sp` | سرعت (۰ تا ۱۰۰) |
| `col` | رنگ (hex) |

پایه‌های LED باید در فهرست پایه‌های امن `1, 2, 12, 13, 14, 38, 39, 40, 41, 42, 47` باشند؛
در غیر این‌صورت درخواست رد می‌شود تا با پایه‌های لمسی/رله تداخل نکند.

## ۲. BLE

### ۲.۱ سرویس

| نقش | UUID |
|-----|-----|
| Service | `6d1e0001-3c4a-4d8f-9b1a-7f2c5e8a9b01` |
| RX (Write) | `6d1e0002-3c4a-4d8f-9b1a-7f2c5e8a9b01` |
| TX (Notify) | `6d1e0003-3c4a-4d8f-9b1a-7f2c5e8a9b01` |

### ۲.۲ قالب پیام

هر فرمان یک شیء JSON است که با `\n` پایان می‌یابد. پاسخ‌ها هم خط‌به‌خط JSON هستند.

```json
{"id":1,"cmd":"state"}
{"id":1,"ok":1,"t":"state","pos":[42,38],"dir":[0,0]}
```

- `id` — شمارهٔ درخواست؛ در پاسخ تکرار می‌شود.
- `ok` — `1` موفق، `0` ناموفق (به‌همراه `err`).
- `t` — نوع پاسخ: `state`، `ack`، `chunk`، …

### ۲.۳ احراز هویت

پس از اتصال، کلاینت باید یک توکن بگیرد و در درخواست‌ها بفرستد. توکن با `esp_random()`
ساخته می‌شود و فقط در حافظه نگه‌داری می‌شود.

### ۲.۴ انتقال داده‌های حجیم

لاگ و CSV برای BLE به قطعه‌های ۱۱۰ بایتی base64 تقسیم می‌شوند:

```json
{"t":"chunk","id":7,"k":"csv","i":0,"n":12,"d":"UkVBRFQs..."}
```

کلاینت باید قطعه‌ها را با `i` مرتب کند تا وقتی `i == n-1` برسد، داده کامل است.

## ۳. پروتکل داخلی پنل

پنل وب از همان endpointهای HTTP بالا استفاده می‌کند و با `fetch` وضعیت را به‌صورت دوره‌ای
(با فاصلهٔ کوتاه) از `/get_sensors` می‌خواند. هیچ WebSocket یا وابستگی سمت سرور وجود ندارد —
پنل کاملاً در `PROGMEM` داخل firmware قرار دارد.
